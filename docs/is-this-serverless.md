# 這真的是 serverless 嗎？有沒有更好的作法？（2026-09-01）

簡答：**是，而且對這個問題來說是對的架構。** 但「serverless」這個詞需要誠實拆解，替代方案也值得記錄。

## 白話版（給非工程師）

「無伺服器」不是「沒有電腦在運作」，而是「**沒有一台你需要照顧的機器**」。

- 你不用租主機、不用裝系統、不用半夜重開機、不用備份資料庫、不用付月費空租。
- 程式放在 Cloudflare 的雲端服務上：有人來投票才運轉、沒人用就閒置歸零，免費方案就能跑一場數百人的討論。
- 你要做的只有兩件事：按一次部署、把連結發出去。

相比之下，官方 pol.is 需要三個常駐程式加一個資料庫，得有工程師照顧。這個專案的目標就是把那個門檻拆掉。

## 技術版：serverless 的三個判準

| 判準 | 本專案 | 說明 |
|---|---|---|
| 不用管理伺服器（no ops） | ✅ | 沒有 VM、容器、OS、資料庫服務要維護；部署即完成 |
| 用多少算多少、閒置歸零（scale to zero） | ✅ | Worker 與 Durable Object 都是 per-request 計費；沒流量就沒成本 |
| 自動擴縮 | ✅（有上限） | Worker 水平擴展；**單場討論**收斂在一個 Durable Object（單執行緒），這是規模上限的來源，也是一致性的來源 |

誠實的但書：

1. **serverless ≠ static**。lifeboat 那種純靜態工具可以整包丟任何空間；Polis 不行——投票是多人共享的可變狀態，加上審核權限，一定要有一個「大家都寫得進去的地方」。Durable Object 是能滿足這件事的**最小**雲端原語。
2. **有廠商綁定，但資料沒有**。程式綁 Cloudflare 的執行環境（換平台要改存取層，數學層與前端可整包搬走）；資料隨時可用匿名化 CSV 全量匯出，沒有被鎖住。
3. **免費方案的實際限額**（2026 時點，每日 00:00 UTC 重置，超過即報錯）：
   - 請求 10 萬/天、SQLite **讀 500 萬列/天、寫 10 萬列/天**、儲存 5GB
   - 真正要小心的是「讀列數」：一句 SQL 掃過幾列就算幾列。本專案已把所有統計反正規化到計數欄（見下），主要動作的成本：投票約寫 2 列／讀 <100 列（回應直接附下一句，省掉一半請求）、看結果頁約 1 請求／讀個位數列（快取命中時）。一場 500 人 × 20 句的工作坊全程約 1.1 萬請求、2 萬列寫入、低於 300 萬列讀取——免費額度內；更大或更頻繁就是每月 5 美元的付費方案（讀寫額度放大千倍）。
   - educational 教訓：2026-09-01 的第一版抽題端點對每句意見跑 COUNT 子查詢掃投票表，一場壓測就燒掉上億列讀取、觸頂鎖站一天。詳見 [stress-test.md](stress-test.md)。

## 考慮過的替代架構

| 方案 | 判定 | 原因 |
|---|---|---|
| **Workers + Durable Object SQLite**（現行） | ✅ 採用 | 一場討論一個物件：天然隔離、強一致、零資源佈建（部署時自動生成）；數學就在資料旁邊算，沒有網路往返 |
| Workers + **D1**（Cloudflare 的共享 SQLite 服務） | ❌ | 要先手動建立資料庫資源（Deploy Button 流程多一步）；所有討論擠一個 DB，隔離與清理都要自己寫；對本案沒有換來任何好處 |
| Workers + **KV** | ❌ | 最終一致性——兩個人同時投票可能互相蓋掉，計票工具不能用 |
| **純 GitHub**（Pages + Issues/Discussions 當投票箱 + Actions 算數學） | ❌（記錄備查） | 真的可以零 Cloudflare：陳述當 issue、表情符號當票、排程 workflow 算分群發佈到 Pages。但延遲以分鐘計、強迫參與者有 GitHub 帳號、API 有速率限制。對「開發者社群、且想要具名可驗證身分」是有趣變體，對一般審議是負擔 |
| **純靜態＋客戶端**（票存瀏覽器，QR/檔案彙整） | ❌（部分場景可取） | delib 的 Power Ranker 走這條路：適合單場實體工作坊離線彙整，但無法做到「陸續有人遠端加入、即時更新地圖」的 Polis 核心體驗 |
| 官方 polis 裝進 Cloudflare Containers | ❌ | delib 的 `docs/polis-hosting.md` 已評估：要付費方案、還是沒有 PostgreSQL，等於半套自架 |

## 現行用法還能更好的地方（已在 backlog）

- **靜態資產已免費**：頁面與 JS/CSS 由 assets 通道直出，不吃 Worker 請求額度（`run_worker_first` 只攔 API 與需要安全標頭的頁面）——已是目前的設定。
- 結果快取已做在討論物件內（變動後最快 2 秒重算一次），對免費額度友善。
- 若未來單場討論衝破數千人：出口是把數學改成增量更新（官方 EMPCA 路線）或分片統計，架構不用換。

## 結論

以「一個審議工作者，零工程資源，要跑完一輪 Polis」為題，**Workers + Durable Object 是目前公有雲上最省事的正解**，不是妥協。更「純」的方案（全靜態、全 GitHub）都會犧牲 Polis 的即時協作本質；更「重」的方案（D1、容器、VM）都在增加要照顧的東西而沒有換到能力。
