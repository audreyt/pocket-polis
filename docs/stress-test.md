# 壓力測試報告（2026-09-01）

問題：**500 人同時對 20 句意見投完整輪，單一 Durable Object 扛不扛得住？**

答案：扛得住，而且有數倍餘裕。可重現：

```bash
node scripts/stress-test.mjs <你自己的部署網址> 500 20 100
```

（腳本會建立標題含「壓力測試」的新討論、模擬完整參與流程——每票前先 `/next` 抽題——並在期間每 5 秒拉一次 `/results` 模擬主持人盯盤，結束時自動關閉討論。只能對自己控制的部署執行。）

## 對 production（polis.mashbean.net）的實測數字

| 項目 | 數字 |
|---|---|
| 規模 | 500 位參與者 × 20 句 = **10,000 票**＋10,000 次抽題 = 20,011 個請求 |
| 總耗時 | **59.3 秒**（並發 100 全速灌入） |
| 吞吐 | **337 請求/秒**（169 票/秒），全程穩定無衰減 |
| 延遲 | 投票 p50 **289ms**、p95 336ms、p99 424ms、最大 500ms |
| 錯誤 | **0 筆** |
| 期間的 `/results`（含重算） | p50 386ms、最大 490ms |
| 結束後全量重算（500×20 矩陣） | 386ms（含網路往返） |

## 事故與後續優化（2026-09-01）

這次壓測**燒穿了免費方案的 SQLite 讀取額度**（每天 500 萬列，超過即整站報錯至 00:00 UTC 重置）：第一版的抽題端點 `/next` 對每句意見跑一個 `COUNT(*)` 子查詢掃投票表——壓測末期每次抽題讀約 1 萬列 × 1 萬次呼叫 ≈ 上億列。當日修正（schema v2）：

| 動作 | 修正前 | 修正後 |
|---|---|---|
| 抽題 `/next` | 每句意見 COUNT 掃 votes（S×P 列/次；500×20 時 ≈ 1 萬列） | 讀 statements 計數欄＋自己的票（≈ 40 列） |
| 投票 | 寫 3 列（票＋revision＋last_seen）＋兩個請求（抽題+投票） | 寫 2 列（票＋計數欄；revision/last_seen 節流）＋**一個請求**（回應附下一句） |
| 首頁/資訊計數 | 全掃 votes | 讀 statements 計數欄（S 列）＋meta（1 列） |
| 管理意見清單 | LEFT JOIN votes 全掃 | 只讀 statements |
| 結果快取命中 | — | 讀 3–4 列；超過 30 秒才做一次 ~S 列的新鮮度探測 |
| 結果重算間隔 | 固定 2 秒 | 隨票數自適應 2→15 秒 |
| 結果頁前端 | 每 30 秒 3 個請求、背景分頁照打 | 每 30 秒 1 個請求、背景分頁暫停 |

同規模（500×20）重跑的預估帳單：請求 2 萬 → **1.1 萬**、列寫入 4.5 萬 → **2 萬**、列讀取 ~1 億 → **< 300 萬**，全部回到免費額度內。schema 遷移包在單一交易內（失敗整包回滾），舊對話首次被存取時自動升級。

## 怎麼讀

- p50 與 p99 只差 ~140ms：Durable Object **沒有排隊崩潰**的跡象，延遲主要是台灣→Cloudflare 邊緣的網路往返，不是伺服端。單 DO 的實際處理成本約 3ms/請求。
- 這個測試比真實世界嚴苛得多：真人每票要看題、想 5–15 秒，500 人「同時在線」的真實尖峰大約只有 30–100 請求/秒——實測的 337 請求/秒代表約 **3–10 倍餘裕**。
- 免費方案額度（10 萬請求/日）下，這樣一場 500 人的工作坊約花掉 2 萬請求，一天可以辦四、五場。
- 外推：規格文件的設計目標「數百～低千位參與者」成立。要到數千人同場，瓶頸依序是單 DO 吞吐（可拆讀寫或分片）與數學重算頻率（已有 2 秒節流），架構內都有出口。
